# GG Media Storage Specification

Status: approved provider-neutral design contract

## Principles

- MongoDB stores media metadata and ownership, not large image/video binary payloads.
- GG-managed object storage is the canonical platform media store.
- Private objects are private by default.
- The browser never receives storage-provider credentials.
- Object keys are generated by the backend and are not accepted as arbitrary user-selected paths.
- A user must have permission to upload, replace, view or delete a media asset.
- Google Drive is optional for personal exports and backups; it is not canonical storage.

## Asset categories

- account/profile images
- World emblems
- Club badges
- Club kits and kit artwork
- training session photographs
- training videos
- facility/map artwork
- attachments and exports

## MediaAsset metadata

Store:
- worldId when the asset belongs to a World
- ownerUserId
- scope (account or world)
- asset type
- provider identifier
- generated object key
- content type
- size in bytes
- optional checksum
- visibility
- linked entity type/id
- processing/upload status
- createdAt/updatedAt

Never store a permanent public URL for a private asset as the only access path. Generate short-lived signed access URLs after backend authorization.

## Upload flow

1. Authenticated user requests an upload.
2. Backend resolves the active World where relevant.
3. Backend checks membership, role, entity relationship, media category and visibility.
4. Backend validates file type and configured size limit.
5. Backend generates a random namespaced object key.
6. Backend creates a short-lived upload authorization (or accepts a streamed upload through the API).
7. Client uploads to object storage.
8. Backend confirms the object, records metadata and marks the asset active.
9. Access is served through an authorized download/signing operation.

Incomplete uploads must expire and be cleaned up. Deletion must remove or tombstone both metadata and object according to retention rules.

## Provider abstraction

Expose a storage adapter with operations equivalent to:
- createUploadAuthorization
- confirmUpload
- createDownloadAuthorization
- deleteObject
- headObject

Provider-specific code stays behind the adapter. Evaluate S3-compatible storage, Cloudflare R2, Railway Buckets and Vercel Blob against price, egress, private access, region, upload constraints, operational complexity and the current hosting topology before selecting one.

## Security

- Validate actual file signatures where appropriate; do not trust filename or Content-Type alone.
- Apply per-category size limits and allow-lists.
- Use random keys and prevent path traversal.
- Keep all credentials in server environment/secret storage.
- Use short expiry times for signed operations.
- Scan/quarantine user-provided media where supported before serving it to other users.
- Enforce visibility at access time; an asset's visibility setting is not sufficient without World/membership checks.
- Private training assets must remain private even when attached to a World session.

## Optional Google Drive integration

Use explicit OAuth consent and minimum scopes. Keep refresh tokens encrypted server-side. Provide disconnect/revoke and data export controls.

Drive is an optional destination for exports/backups. If Drive is disconnected or unavailable, GG remains fully usable.
